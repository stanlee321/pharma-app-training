# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**TivaTrainer** — a SwiftUI (iOS 17+) pharmacokinetic simulation app for anesthesiologists. It computes and visualizes drug concentration curves for Total Intravenous Anesthesia (TIVA) using Target-Controlled Infusion (TCI). An anesthesiologist picks a drug/PK model, enters patient biometrics, sets target concentrations, and the app returns bolus/infusion dosing plus plasma (Cp) and effect-site (Ce) curves, rendered as an interactive chart and a 2D/3D compartmental animation.

Four PK models are implemented: Propofol (Marsh, Schnider), Remifentanil (Minto), Dexmedetomidine (Hannivoort) — all as a 3-compartment mammillary model + effect site (4-state ODE).

The repo now holds **three connected parts**:

1. **iOS app** (`PharmaApp/`) — opens on a mock login → Encounter List → Encounter Hub → clinical section screens (patient data, pre-anesthetic assessment, technique, monitoring, drug ledger, fluid balance, recovery, newborn, review/export). Clinicians fill in an `AnesthesiaCase`. The original PK screens (drug selection → patient input → simulation → compartmental) are still there as reusable tools.
2. **Backend** (`backend/`) — FastAPI + SQLAlchemy 2 + Alembic service that stores cases and renders **filled PDF forms** (`/api/v1`).
3. **Forms-parsing pipeline** (`notebooks/forms/`) — Python (PyMuPDF) that turns the source anesthesia PDFs (`notebooks/data/`) into 1:1 vector clones plus field-schema JSON (`notebooks/forms/schema/`). The backend's fill-pdf renderer draws case data onto those clones, so backend export depends on this directory.

> ⚠️ **No PK regression tests exist.** Schnider shipped with V3 10× too small and no V2 age term (fixed 2026-09-16) because nothing checks the model parameters against `04_Validation_Reference.md`. When touching any `*Params(patient:)`, verify by hand against the published model and update the spec docs and `generate_mock_data.swift` too.

## Build & run

The Xcode project is **generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`** — do not hand-edit `PharmaApp.xcodeproj`, it is a build artifact. Sources are picked up automatically from the `PharmaApp/` directory tree, so:

```bash
xcodegen generate          # regenerate after ANY file add/rename/move — new .swift files won't be in the target otherwise
open PharmaApp.xcodeproj    # team 923BHPTBX7 is set in project.yml; pick a device/simulator, Cmd+R
```

Command-line build/test (no XCUITest scheme is configured; adjust the destination as needed):

```bash
xcodebuild -project PharmaApp.xcodeproj -scheme PharmaApp \
  -destination 'platform=iOS Simulator,name=iPhone 15' build
```

The iOS app has **no test target and no lint config**. The "Validation Reference" (`docs/reference/rust-engine-spec/04_Validation_Reference.md`) holds hand-calculated expected values, but no XCTest suite uses them. Do not claim Swift tests pass; there are none to run. (The only automated tests are the backend's pytest smoke tests, below.)

### Backend (`backend/`, run all commands from inside it)

```bash
conda activate tiva_backend                 # Python 3.11; pip install -r requirements.txt
docker compose -f ../docker-compose.yml -f ../docker-compose.dbport.yml up -d db  # optional local Postgres on host port 5433 (the shared stack keeps it internal)
export TIVA_DATABASE_URL=postgresql+psycopg://tiva:tiva@localhost:5433/tiva   # omit → SQLite ./tiva.db
alembic upgrade head
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload   # 0.0.0.0 so a physical device can reach it; docs at /docs
python -m pytest                            # smoke tests (pin their own SQLite DB)
python -m pytest tests/test_smoke.py::test_case_lifecycle  # single test
TIVA_API=http://127.0.0.1:8000/api/v1 python scripts/e2e.py  # e2e against a RUNNING server; writes PDFs to notebooks/forms/out/
```

Settings live in `app/core/config.py` (env prefix `TIVA_`). Layers run config → db → domain (`derivations.py`) → application (`CaseService`, snake_case Pydantic DTOs) → infrastructure (repository, `render/` fill-pdf + `crosswalk.py`) → api (`api/v1/routes_*.py`). The service **trusts the `X-User-Id` header** for tenant scoping and has no auth of its own. Never expose it publicly without the API gateway in front. `backend/README.md` is partly stale (its export is no longer summary-only); `docs/wiki/backend-api.md` is the current reference.

### Forms pipeline

Uses the conda env `forms_p11`. From `notebooks/`: `python forms/regen.py data/<file>.pdf forms/out/<slug>_clone.pdf` (clone) and `python forms/schema_extract.py data/<file>.pdf <form_id> forms/schema/<slug>.schema.json` (schema). The traps that commonly break it are in `notebooks/docs/parsing-wiki/cold-resume.md`.

### Regenerating mock simulation data

The app bundles pre-computed simulation snapshots in `PharmaApp/Resources/MockData/*.json`. Regenerate them with the **standalone script** (its PK types are duplicated inline so it runs without the app):

```bash
swift generate_mock_data.swift   # writes 5 JSON files into PharmaApp/Resources/MockData/
```

Note: `PharmaApp/Engine/MockDataGenerator.swift` is an *in-app* equivalent (uses the real engine types), separate from the standalone script. Keep the two scenario lists in sync if you change either.

### TestFlight

Bump `CURRENT_PROJECT_VERSION` in `project.yml` for each upload, then `xcodegen generate`, then Xcode → Product → Archive → Distribute.

## Architecture

### The engine abstraction is the central seam

All PK/PD math lives behind `PKEngineProtocol` (`Engine/PKEngineProtocol.swift`), with two implementations selected by a single compile-time switch:

```
PKEngineProtocol
 ├── MockPKEngine   (Engine/MockPKEngine.swift)  — the ONLY working engine today; a real RK4 ODE solver
 └── RustPKEngine   (Engine/RustPKEngine.swift)  — production stub; every method is fatalError()
```

`EngineProvider.useMock` (`Engine/EngineProvider.swift`) chooses between them. It is `true` and must stay true until the Rust C-FFI library exists — flipping it to `false` today crashes the app. The Rust replacement is fully specified in `docs/reference/rust-engine-spec/` and `docs/reference/technical/02_FFI_Integration_Guide.md`; `SimulationTypes.swift` deliberately mirrors the `#[repr(C)]` FFI contract so the Swift call sites don't change when the engine is swapped.

`MockPKEngine` is **not fake data** — it integrates the 4-state ODE with RK4 and runs the BET (Bolus-Elimination-Transfer) TCI algorithm. Per-model patient parameters (V1/V2/V3, clearances, ke0) are computed from covariates in the `*Params(patient:)` methods.

### Unit conventions (critical — the most common source of bugs)

The engine works internally in **mg** (amounts) and **mg/ml** (concentrations) and **ml** (volumes). Display units differ per drug and are reached by multiplying by `PKParams.displayFactor`:
- Propofol → `×1000` (mg/ml → mcg/ml)
- Remifentanil / Dexmedetomidine → `×1_000_000` (mg/ml → ng/ml)

Rate constants (k10, k12, …, ke0) are **per minute**, but time in the simulation loop is tracked in **seconds** — the RK4 step is called with `dt/60` to reconcile. Target concentrations coming from the UI are in display units and must be divided by `displayFactor` before entering the engine. When touching any math, check which unit space you are in.

### State & data flow

- One `AppState` (`App/AppState.swift`, `@MainActor @Observable`) is the single source of truth: auth/author, `navigationPath`, the case store, and the PK state (selected drug, `PatientProfile`, `[TargetEvent]`, `SimulationOutput`, playback state, engine handle). It is injected once via `.environment(appState)` in `PharmaApp.swift`.
- ViewModels (`SimulationViewModel`, `CompartmentalViewModel`) are thin `@Observable` wrappers that hold a reference to `AppState` and derive chart/animation state from `appState.simulationOutput`. They do not own the data.
- Screen flow: `RootView` shows `LoginView` until `appState.isAuthenticated`, then shows a `NavigationStack(path: $appState.navigationPath)` rooted at `EncounterListView`. Every destination is a case in the `Route` enum (`App/Route.swift`); clinical routes carry the case `UUID`, and `.technique` also carries a `TechniqueZone`. To add a screen, add a `Route` case and add it to the `destination(for:)` switch in `RootView`. The launch modal is a one-time overlay gated on the `hasSeenAnnouncement_v1` `@AppStorage` flag.

### Clinical-record persistence (the second seam)

`Models/ClinicalRecord.swift` defines the `AnesthesiaCase` aggregate. Screens bind to `MockCaseStore` (`Services/CaseStore.swift`), which adapts a **`CaseBackend`** port (`Services/CaseBackend.swift`):
- `InMemoryBackend` (actor, offline/previews) or `RestBackend` (live FastAPI). Chosen by `CaseStoreProvider.useREST` in `App/CaseStoreProvider.swift`, currently `true`.
- `save` is a **full-aggregate `PUT /cases/{id}`**, and the client owns the id. Screens never call `URLSession` directly.
- The base URL is a runtime setting: the Login "Server" field, persisted in `UserDefaults` under `backend_base_url` (default is a hard-coded Mac LAN IP for physical-device testing). ATS allows local networking via `project.yml`.
- `RestBackend` sends a stable per-device UUID as `X-User-Id` (a mocked API-gateway tenant; guest→parent owner). See `docs/wiki/backend-api.md` "Gateway integration".
- Export (`exportForm(caseID:formID:)`) asks the backend to fill one of the 4 form templates. Swift model field names must stay in sync with the backend DTOs (JSON snake_case) and with the PDF crosswalk.
- Drug database: `DrugModel`/`DrugDatabase` load `Resources/drug_models.json` with `.convertFromSnakeCase` decoding, falling back to `DrugDatabase.hardcoded` if the bundle load fails. Each `DrugModel.rustModelId` (`"marsh"`, `"schnider"`, `"minto"`, `"hannivoort"`) is the key that maps a UI drug entry to an engine model — this string is what gets passed to the engine, not the `DrugModel.id`.

### Two interaction hotpaths

- **Target drag** (`SimulationViewModel`): dragging the target node calls `engine.computeTCI(...)` on every change to update bolus/infusion readouts live — required to stay under 16ms (60fps). Releasing ("Done") triggers a full `engine.simulate(...)` re-run and re-scales the axes.
- **Rendering**: the chart (`Views/Simulation/ChartCanvas.swift`) and the 2D compartmental view (`Views/Compartmental/CompartmentCanvas.swift`) are hand-drawn with SwiftUI `Canvas`. The 3D compartmental view (`Views/Compartmental/CompartmentSceneView.swift`) is SceneKit (`SCNCylinder` glass compartments, `SCNParticleSystem` flow along pipes), toggled via `CompartmentalViewModel.use3D`.

## Conventions to follow

- **Strict concurrency is on** (`SWIFT_STRICT_CONCURRENCY: complete` in `project.yml`). All model/output types are `Sendable`; engines are `@unchecked Sendable`; UI state classes are `@MainActor`. New engine-crossing types must be `Sendable`, and new UI state must respect the main-actor isolation.
- Use the `@Observable` macro (not `ObservableObject`/`@Published`) and `.environment(...)` injection — this codebase is on the iOS 17 observation model throughout.
- Don't put `.accessibilityElement(children: .combine)` on rows that contain editable text fields. It made them un-editable on device.
- **Gated actions: propose them, never run them yourself:** `git push`, repo/org transfer, TestFlight or prod deploy, and anything touching real patient data. **PHI:** `notebooks/data/*.pdf` and `notebooks/forms/imss/` may contain patient data. Never copy patient values into docs, wikis or commits (structure only).
- Centralized styling lives in `Utilities/DesignSystem.swift` (`AppColors`, `Font` extensions, `Haptics`, `Spacing`). Reuse these rather than introducing ad-hoc colors/fonts; the curve/compartment color meanings (cyan = plasma, green = effect, orange = infusion) are consistent across chart and animation.
